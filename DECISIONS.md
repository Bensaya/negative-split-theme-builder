# Decisions

The choices that shaped this build, each with the alternative it beat. Written
for someone who does not work in frontend daily.

## 1. The theme is one typed object
**Decision:** Every setting lives in a single `Theme`; the option lists are
`as const` and the types derive from them (`src/theme/theme.ts`).
**Why:** Adding an option widens the type, the URL validator, the Shuffle space
and the sidebar at once, so those four cannot drift apart.
**Alternative rejected:** Loose strings with a separate list of valid values;
nothing then stops the URL parser accepting a radius the sidebar cannot show.

## 2. Curated presets over free-form values
**Decision:** Colour, radius and the two menu dimensions are finite, curated
sets — Tailwind ramps and four radius steps (`src/theme/theme.ts`). The two
font fields are the deliberate exception: they are open strings resolved
against the catalogue (see 10).
**Why:** The brief defines these as discrete options, and shadcn's own create
page works the same way. A finite set is also what makes the contrast
guarantees testable rather than aspirational: `src/theme/tokens.test.ts` walks
all 60 base × theme combinations for primary text and all 240
base × theme × menu combinations for the bag badge, asserting WCAG AA on each.
URL validation becomes a membership check over short readable values
(`theme=amber`), and Shuffle draws from options already known to work.
**Alternative rejected:** Free-form hex and a radius slider. More brand
flexibility, but they need a generated ramp per colour, contrast guarantees
that only hold at runtime, and raw input sanitised before it reaches CSS.
**Extension path:** A "Custom" option beside the presets — a validated hex
param, an OKLCH-generated ramp, and the existing `pickForeground` search
(`src/theme/contrast.ts`). Presets stay the default.

## 3. The preview is themed by CSS variables on a wrapper, not `:root`
**Decision:** `resolveTokens()` returns plain custom properties, spread onto the
single `<div>` wrapping the storefront (`src/theme/tokens.ts`, `src/App.tsx`).
**Why:** shadcn declares its tokens in Tailwind's `@theme inline`, so
`bg-primary` compiles to `background-color: var(--primary)` — one level,
resolved on the element itself. Inheritance does the propagation, so there is no
"apply the theme" step, and the builder's own chrome keeps the default theme.
**Alternative rejected:** An `<iframe>`; real isolation, but you re-inject the
stylesheet, font loading gets awkward, and container queries lose their point.

## 4. Three consequences of `@theme inline`
**Decision:** The wrapper carries `bg-background text-foreground font-sans`;
code uses `var(--primary)` and never `var(--color-primary)`; the storefront uses
semantic tokens only, never `bg-red-500`.
**Why:** shadcn puts the first three on `body`, outside the subtree;
`@theme inline` never emits `--color-*` into `:root`; and stock palette
utilities are not subtree-overridable, so they would ignore the theme.
**Alternative rejected:** Plain `@theme`; it resolves the inner `var()` at
`:root`, so a per-subtree override is silently ignored.

## 5. Colours come from the installed Tailwind
**Decision:** `src/theme/palette.ts` is generated by
`scripts/generate-palette.mjs`. Base colours start from the five the brief
names — Neutral, Slate, Gray, Zinc, Stone — taken from Tailwind's neutral
ramps, and are extended by three tinted ones (#16).
**Why:** Tailwind v4 ships oklch and re-tuned its ramps, so remembered hex codes
are wrong. shadcn has since dropped Slate and Gray, but Tailwind still has all
five, so deriving from Tailwind matches the brief and survives shadcn changing.
**Alternative rejected:** shadcn's current seven presets; more current, and
visibly contradicts the specification we were given.

## 6. Contrast is real WCAG 2.1, and readable colours are searched for
**Decision:** `src/theme/contrast.ts` converts oklch to sRGB before applying the
WCAG formulas. `pickPrimary()` takes the brightest accent step that clears AA;
`pickAccentOn()` also requires that text on the accent clears AA.
**Why:** oklch's `L` is perceptual lightness, not WCAG luminance — close enough
to look right, wrong often enough to ship unreadable text. Both searches came
from tests: a fixed shade put `rose-600` at ~4.4:1, and checking only accent
visibility left the bag count unreadable in 14 of 240 combinations.
**Alternative rejected:** Thresholding oklch's `L` with one hardcoded shade per
role; three lines, and either too dark everywhere or below AA somewhere.

## 7. Menu controls are Default/Inverted and Subtle/Bold
**Decision:** Two two-way toggles rather than two free colour pickers.
**Why:** All four combinations are readable by construction, deriving from a
base pair whose contrast is already settled. It is also what shadcn does — the
generated `components.json` carries `menuColor` and `menuAccent`.
**Alternative rejected:** Free colour pickers; they let a user produce a menu
that is technically readable and still ugly.

## 8. React owns the theme; the URL is a projection of it
**Decision:** One `Theme` in React state. Every edit goes through a single
`applyTheme()`, the only writer of the URL, using immediate `replaceState` with
no debounce and no `pushState` (`src/url/useThemeUrl.ts`).
**Why:** The flow is acyclic only because `pushState` and `replaceState` do not
fire `popstate`, so a write can never trigger a read and no guard flags are
needed. All seven controls are discrete, so a debounce would coalesce nothing
and add stale writes.
**Alternative rejected:** Two-way sync; state writes the URL, the write triggers
a read, the read sets state, and you add flags to break cycles you created.

## 9. Readable query parameters, validated per field
**Decision:** `?v=1&base=slate&theme=rose&radius=large&...` — each parameter
checked independently, an invalid value defaulting that field alone. A missing
or empty `v` means version 1; an unsupported one falls back and leaves the URL
untouched (`src/url/urlCodec.ts`).
**Why:** A reviewer can read the link and hand-edit one field. It is also
shorter than base64, which inflates by a third: 101 characters against 135. And
a shared link is untrusted input, so rewriting the address bar would destroy the
evidence in the one case someone is debugging.
**Alternative rejected:** A base64 blob with all-or-nothing validation; opaque,
undebuggable, still needs a version marker, and one bad character costs the
other six settings.

| Case | Behaviour |
| --- | --- |
| No query string | Default theme |
| Unknown value (`base=chartreuse`) | That field defaults, others kept |
| Unknown parameter | Ignored |
| Duplicated parameter | First wins |
| `v` missing or empty | Treated as version 1 |
| `v` present but unsupported | Whole theme defaults, notice shown, URL left untouched |
| Font name over 64 chars, or containing control characters | That field defaults |

## 10. Fonts resolve against the catalogue, not the browser
**Decision:** `decode()` carries font names through as opaque strings;
`resolveFamily()` matches them case-insensitively once the catalogue exists,
correcting spelling and defaulting anything unknown. The catalogue comes from
the Web Fonts Developer API, falling back to 35 curated families without a key.
**Why:** `decode()` is synchronous and the catalogue is a network call, so eager
validation would replace a shared link's typography with the default before the
response arrives — and permanently if there is no key. `.env.local` is
gitignored, so the fallback is the path a reviewer actually hits.
**Alternative rejected:** Asking the browser whether it can render the name; it
would accept `Helvetica Neue` on a machine that has it, so the link would look
right only to the sender.

Two Google APIs are involved, with opposite requirements: the Developer API
needs a key and returns the catalogue, while the CSS2 API needs no key and
returns the font files. The key gates the *list*, never the rendering, which is
why a catalogue failure does not stop a font the user already asked for from
loading.

When a font does fail, the requested family stays in the theme and in the URL.
The storefront shows fallback type, a notice explains, and re-picking that same
family triggers an explicit retry: re-selecting the already-selected family
changes no theme value, so the loader is asked directly rather than the theme
being nudged into forcing a re-run.

## 11. Previews use each family's `menu` subset, under an alias, virtualised
**Decision:** The picker registers the API's `menu` file through
`new FontFace(alias, ...)` and renders only the visible rows of ~1,950 families
via `@tanstack/react-virtual` (`src/fonts/preview.ts`, `FontPicker.tsx`).
**Why:** Choosing the face name means a preview can never be mistaken for a full
font; a family-keyed cache would report a hit and leave the storefront with only
the letters of that font's name. Search filters the whole catalogue before
windowing, or it would only find what happened to be mounted.
**Alternative rejected:** Batching families into one CSS2 request with `text=`;
every scroll window is a novel URL, so scrolling back never hits the cache.

## 12. The preview responds to its own width
**Decision:** The storefront uses container queries; a Desktop/Mobile toggle
constrains the preview box.
**Why:** It should reflow because the preview is narrow, not because the window
is. Without the toggle the distinction is invisible and the claim untestable.
**Alternative rejected:** Viewport media queries inside the storefront; they
answer the wrong question for a preview pane.

## 13. Custom feature: Save & Compare
**Decision:** One in-memory snapshot, a read-only Saved/Current toggle, and an
explicit restore.
**Why:** The builder makes exploration feel risky: once you like something,
changing it costs you the thing you liked. It also reuses what exists — a
snapshot is a `Theme`, so it serialises through the same `encode()`, and the
comparison renders the same storefront with a second token set, which works only
because theming is scoped to a wrapper.
**Alternative rejected:** Multiple named snapshots in `localStorage`; a list UI,
deletion, quota handling and migration, for a feature whose real question is
"was the last one better?". The snapshot is held in memory for the
page session and is lost on refresh, deliberately: the shareable URL is already
the durable mechanism, so this one is the scratch pad.

## 14. Test the logic hard, do not unit-test the pixels
**Decision:** Unit tests cover the pure modules — contrast, token resolution,
URL coding, catalogue fallback, font-load recovery. Playwright covers the two
journeys that only exist in a browser: the shared link round-trip and Save &
Compare. No component tests in between.
**Why:** The pure modules are where correctness is subtle and invisible — the
AA failures in 6 were found by an exhaustive test before any UI existed. The
two journeys are the opposite case: nothing below the browser can prove that a
link restores a theme, or that comparing leaves the URL alone. Both e2e specs
run without an API key, so they exercise the fallback catalogue a reviewer sees.
**Still uncovered:** keyboard navigation in the font picker — arrow keys across
the virtualised boundary, Tab leaving the popover, and
`aria-activedescendant` never naming an unmounted row. Those were checked by
hand and are not re-run by CI.
**Alternative rejected:** Component tests for every control; hours asserting
that a click calls a setter, competing with the design work the brief grades.

## 15. The page takes the base tint; cards stay white
**Decision:** `--background` is the chosen base ramp's `50`, while `--card` and
`--popover` stay pure white. Product photography sits on `bg-card` rather than
on the page.
**Why:** the base colour was previously invisible. Every large surface was
hardcoded white, and Tailwind's five neutral ramps are near-achromatic at light
steps — 3 RGB points apart at `50`, 6 at `100`. Putting the tint on the biggest
surface is the only place it registers at all, and splitting page from card
gives the storefront a second benefit it was missing: cards now read as objects
instead of dissolving into the page, and the white-background studio shots stop
floating as bare rectangles.
**Alternative rejected:** amplifying the ramp's hue to make the difference
obvious. It would work, and it would mean the colours are no longer Tailwind's
own (#5) — a large change to defend for a control the brief describes as a
neutral choice. The honest answer is that base colour is a temperature control,
most visible with the menu inverted, where the ramp's `950` step carries it.

## 16. Three tinted base colours, on top of the five
**Decision:** Base colour offers Sand, Sage and Ice alongside the five the
brief names. They draw from Tailwind's `amber`, `emerald` and `sky` ramps,
mapped through `BASE_RAMP` in `theme.ts`. `--muted-foreground` is now searched
for rather than fixed at shade 600.
**Why:** the five neutral ramps are 3 RGB points apart at the page surface and
1 point apart at shade 50 for Stone against Neutral. The control was wired
correctly and did nothing anyone could see (#15). No amount of remapping fixes
that, because the difference is not there in the palette — it needs ramps that
carry chroma, and the tinted three sit 11 to 16 points from Neutral. They are
named for the surface they produce, not their ramp: Amber and Cyan are already
*theme* colours, and one word for two controls is a worse problem than a new
name. The search for muted text is the necessary consequence — `amber-600` on
`amber-50` is 3.08:1, below AA for the spec lines that use it, while every
tinted ramp clears AA at 700. The five neutrals still resolve to 600, so they
look exactly as they did.
**Alternative rejected:** replacing the five with tinted ramps, which would
read as ignoring the specification; and keeping five and amplifying their hue
past what Tailwind ships, which breaks #5 for every base rather than adding
three that are honestly labelled as extras.

## Deferred, deliberately
- **Dark mode.** Doing it properly doubles every colour decision and every
  contrast check, and the brief does not ask for it. The `.dark` block was
  removed rather than left as dead CSS implying a feature that does not exist.
- **Short links.** There is no server, so two long font names make a URL of
  roughly 150 characters. With a backend, POST the theme and return an id,
  keeping the readable URL as the inspectable fallback.
- **Keyboard coverage in CI.** The shared link and Save & Compare journeys now
  run in CI under Playwright. Font-picker keyboard navigation does not: it
  needs assertions about virtualised rows and `aria-activedescendant`, which is
  a larger piece of work than the two journeys were.
